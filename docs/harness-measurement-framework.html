Measuring the SDLC Harness

A measurement framework for the eight-stage Claude pipeline — what to track, what to refuse to track, and how to instrument it across 145 repositories.

8 pipeline stages ~15 skills 145 repositories Azure DevOps · Jira · SonarQube
01

Two rules before any metric

Baseline before rollout

Almost every number below is meaningless without three to six months of pre-harness history. Pull it from Azure DevOps and Jira now, while adoption is still narrow enough that the history is clean.

Every speed metric needs a paired counter-metric

Faster PRs mean nothing if change-failure rate doubles. Track them as pairs, never in isolation. Throughout this document, the counter-metric column is not optional garnish — it is the half that makes the first half credible.

And two anti-metrics to refuse outright

Do not track
  • Lines of code generated. Rewards volume over judgement.
  • Percentage of code written by Claude. Gameable within a sprint, and it measures input rather than outcome.
02

Adoption & harness health

Leading indicators. You cannot attribute outcomes if nobody is using it, and programme-wide averages hide the truth.

MetricWhy it earns its place
Weekly active devs ÷ eligible devsThe denominator matters — eight enthusiasts is not adoption
Sessions per active dev per weekSeparates “tried it once” from “depends on it”
Per-agent and per-skill invocation countsWhich of the 8 stages and ~15 skills actually earn their keep. Expect a long tail of dead weight — delete it
Repo coverage (repos touched ÷ 145)Reveals whether it works on cpp-context-* but falls over on Terraform or Angular
Abandonment rateSessions that start at stage 1 and never reach stage 5. High means the pipeline is too heavy for real work
4-week retentionDevs who tried it and stopped are your most informative population. Interview five of them

The per-skill breakdown is the highest-value item here and the one teams routinely skip. It tells you what to invest in and what to cut.

Flow & productivity

Time to scaffold a Spring Boot service: template skill → green CITemplate deviation rate (ADRs raised)

Watch p90, not just median. AI assistance typically compresses the tail — the “I have never touched this repo before” tasks — far more than the median. A median-only view will systematically understate the effect across a 145-repo estate.

Onboarding is the platform’s real pain, and time-to-first-PR is where the harness should shine loudest. Service scaffolding is the cleanest attributable win available: isolated, repeatable, and easy to time deliberately.

05

Gate rejection rate — the harness-specific one

This is the metric worth building deliberately, because nothing off-the-shelf produces it. At each of the six human gates, record whether the reviewer accepted, edited, or rejected the agent’s artefact — and the edit distance on the ones they accepted.

Read it in both directions. A requirements-analyst rejected 60% of the time is a prompt problem you can fix this week. A code-reviewer rejected 5% of the time may instead mean humans have stopped reading — which is the more dangerous failure, and invisible in every other metric here.

06

Developer experience

Quantitative data will not tell you whether people like this. Run a short quarterly survey — six to eight questions, two minutes.

QuestionWhat it surfaces
Perceived productivity change (5-point)The headline the programme board will ask for
Confidence in harness output reaching productionTrust, which predicts adoption better than satisfaction does
Time lost correcting harness outputThe counter-metric for satisfaction
Cognitive load across 145 repos, before vs. nowThe platform’s central DX problem
Frustration hotspots (free text)Where the real defects are. Read every response
eNPS for the harness itselfTrendable across quarters
07

Instrumenting it in your stack

Local commit
SHA index

Do this first. Record which commits the harness produced. Without it you cannot segment anything in sections 03 or 04, and retrofitting it later is impossible. Keep the marker out of the commit message — most CPP repos are public, and an AI-assistance trailer there is permanent and unretractable. Git hooks write the SHA to a local index instead; the assisted/unassisted split then lives in Azure DevOps, which is not public.

Claude Code
OTel telemetry

Set CLAUDE_CODE_ENABLE_TELEMETRY and export to your existing observability backend. Gives you session counts, tool calls, and token spend — most of section 02.

PostToolUse hook
in settings.json

The only reliable way to capture per-skill and per-agent invocations and gate decisions. A hook logging Skill and Agent calls to a shared store produces the breakdown in sections 02 and 05.

Azure DevOps
+ Jira APIs

Cycle time, lead time, change failure rate, CI first-pass rate, rework. All derivable from data you already hold.

SonarQube API

The full quality trend series, already collected by the parent POM chain. Pure reporting work, no new instrumentation.

08

A realistic starting set

Do not build all of the above. Ten metrics, reviewed monthly, will tell you almost everything the full framework would.

  1. Weekly active devs ÷ eligible
  2. Per-skill invocation counts
  3. Cycle time — median and p90
  4. PR review turnaround
  5. Change failure rate
  6. Defect escape rate
  7. CI first-pass rate
  8. SonarQube critical issues on new code
  9. Gate rejection rate by stage
  10. Quarterly DX survey

Expect the honest answer at three months to be that adoption is uneven and two skills are doing eighty percent of the work. That is a useful finding, not a failure — and it is precisely the one that tells you where to spend the next quarter.
